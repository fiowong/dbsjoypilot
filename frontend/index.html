Reading this against the control chain

The diagram above numbers its boxes 0–16. The sixteen-stage control chain on the main screen is the same walk with the same names, numbered 0–15, and the two agree exactly on 0–8. After that:

  • Box 8 covers two stages. The diagram draws the Validation Agent and its “checks against original words” as one box; the chain runs the agent (stage 8) and the deterministic comparator (stage 9) separately, because one is a model and one is code.
  • The Banking Policy Check is one stage, not four. The dashed block holds boxes 9–12. The chain runs the policy, risk and velocity checks as one stage (index 10), because they read the same resolved draft and share one decision. It runs the field-by-field confirmation as its own stage (index 11).
  • So from chain index 11 on, the chain index is the diagram number minus one. Nothing is missing and nothing is duplicated; the two are the same path at two different resolutions. The Execution-path page shows it stage by stage.

The five agents

Four agents sit in the payment control chain. The fifth, the Personalization Agent, runs next to it and only changes how Joy asks. Each agent makes one decision and returns typed JSON. None of them holds a signing key, a gateway credential or ledger access.

What keeps the agents in check

  • A model's output is data, never an instruction. Every agent returns JSON that is parsed against a strict schema. Anything out of shape is rejected and the turn falls back, so it can never be read as a command.
  • The Validation Agent works on its own. At stage 8 it never sees the other agents' reasoning. It reads the saved evidence and the draft, checks each field, and returns PASS or FREEZE. Stage 9 is plain code that checks that answer again.
  • If a model fails, the rules take over. If an agent times out or returns something malformed, its deterministic mock answers instead. The answer can get plainer, never less safe.
  • Words cannot move money. No prompt, in any language, can produce a signature, an approval or a ledger write, because those live in code the models cannot call.

The sixteen-stage control chain, in order

Stages 3, 4, 5 and 8 are the only stages in the chain that call a model. Everything else is code, and there is code before and after each model stage. The AI stages can only propose; the code stages decide.

What is simulated and what is real

Two things in this build are mocks, and both are named on the screen. Everything either side of them is the live system.

LIVE: running for real in this demo

  • Speech recognition. Tencent Cloud ASR. Audio goes up, text comes back, in English, Mandarin and Bahasa Melayu.
  • Speech synthesis. Cartesia Sonic by default, with English, Mandarin and Malay voices; TRTC Mode switches to Tencent Cloud TTS. The top bar shows which engine is speaking, and says so if it ever has to fall back.
  • The five agents. Real model calls over HTTPS when a model key is configured, each with a typed JSON schema, a retry budget and a hard deadline. Without a key, or if the model is unreachable, each agent runs its deterministic mock instead, and its card says engine: mock. It never silently pretends.
  • The sixteen-stage control chain. Plain deterministic code. No model can call into it, skip a stage, or reorder one.
  • The audit ledger. Append-only and hash-chained: every event carries the hash of the event before it, so editing history breaks the chain visibly.
  • The payload signature. An HMAC-SHA256 signature over the canonical payload, re-verified at the gateway before anything is allowed to execute. The key is a server-held demo key, not a bank HSM.
  • Guardrail screening. The Guardrails Agent's verdict is backed by code: a scam-typology table (government impersonation, romance, tech support, secrecy and more), amount, velocity and payee rules. Code can make the verdict stricter, never looser.

SIMULATED: on purpose, and labelled

  • Customer approval. A mock biometric adapter stands in for FaceID. It returns the same verdict shape the real one would, and it is the only thing in the system that can authorise a payment.
  • The payment itself. A restricted mock capability writes to a synthetic ledger. No money moves, no real account is touched, no bank system is contacted.
  • The customer. “Mei Ling” and “DBS Savings ending 1234” are synthetic fixtures, not real customer data.
  • Payees and balances. Fixtures, resolved through the same code path a real directory would use, so the resolution logic is exercised rather than bypassed.

Why the boundary sits exactly there: the biometric sensor and the payment ledger are the two places a prototype cannot legally or practically reach. Everything either side of that line is the real thing.
